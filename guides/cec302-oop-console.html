General Knowledge 28 marks

Compilation rules, naming, classes vs objects, constructors, interfaces.

a) File name for public class InventoryManager {}›

Must be InventoryManager.java — exactly matching, case included. A public class must live in a file named after itself.

b) Which of the three declarations causes a compile error?›

VALID double annual_Salary = 50000.0; — underscores are legal.

ERROR int 2ndPlaceWinner = 14; — identifiers can never start with a digit.

VALID String $userToken = "A1BF3"; — $ is a legal first character.

c) Naming convention for Classes vs Methods/Variables›

Classes → UpperCamelCase (PascalCase): BankAccount, ShapeApp

Methods / variables → lowerCamelCase: calculateArea(), accountBalance

d) Class vs Object — structural relationship›

A class is the blueprint (fields + methods, no memory for data). An object is an instance created with new — real memory, real values.

If no constructor is written, Java automatically inserts a default no-arg constructor that sets fields to defaults (0 / false / null).

e) Primary role of a constructor›

To initialize an object's state the instant it's created — assigning starting field values, typically from parameters. Same auto-generation rule as (d) applies if none is written.

f) Why no multiple class inheritance — and how interfaces solve it›

Extending two classes creates the diamond problem: ambiguity if both parents define the same member. Interfaces avoid this because they only declare method signatures — no conflicting state.

class Sample implements InterfaceA, InterfaceB { }
g) Obligation created by public void processData(); in an interface›

The implementing class must override it with a matching signature. If it doesn't, and isn't itself declared abstract, the code fails to compile.

Classes and Objects 17 marks

this, field hiding, and tracing the BankApplication array logic.

a) Why is this necessary on lines 5–6 of the Student constructor?›

The constructor parameters (name, age) are named the same as the fields — the parameter shadows the field. this.name means "the field on this object"; a bare name means the parameter. Drop this and you just reassign the parameter to itself — the field is never set.

b) Exact output of Child's showPrices()›

Fields aren't polymorphic — resolved at compile time by declared type.

80.0 50.0

this.price → Child's own field (80.0). super.price → explicitly reaches Parent's hidden field (50.0). This is field hiding, not overriding.

c-i) Array empty → createAccount("Alex", 150.0) → accountCount = ?›

0 < 50 is true → stored at accounts[0], then incremented. accountCount becomes 1.

c-ii) At exactly 50 accounts, createAccount("Sam", 40.0) is called — what happens?›

accountCount < MAX_ACCOUNTS → 50 < 50 is false. The body never executes — the account is silently not created. No exception, no error.

c-iii) Why check index < accountCount instead of index < MAX_ACCOUNTS?›

MAX_ACCOUNTS is just array capacity (50 slots reserved). accountCount is how many are actually filled. Slots beyond it are still null. Using MAX_ACCOUNTS would let you index into a null slot → NullPointerException.

iv) Trace: createAccount(UserA,300) → createAccount(UserB,600) → deposit(0,50) → withdraw(1,200)›
  • accounts[0] = UserA, 300.0  →  count=1
  • accounts[1] = UserB, 600.0  →  count=2
  • deposit(0,50): 300 + 50 = 350.0
  • withdraw(1,200): 200 ≤ 600, so 600 − 200 = 400.0
accounts[0].balance = 350.0 accounts[1].balance = 400.0 accountCount = 2
v) Modify withdraw() so a minimum 10.00 must remain after the transaction›
public static void withdraw(int index, double amount) {
    if (index >= 0 && index < accountCount 
        && amount <= accounts[index].balance 
        && (accounts[index].balance - amount) >= 10.00) {
        accounts[index].balance -= amount;
    }
}

The new clause computes the balance after the withdrawal and only proceeds if it's still ≥ 10.00 — enforcing a minimum balance floor.

Inheritance and Polymorphism 26 marks

Tracing ShapeApp, dynamic dispatch, and extending the Shape hierarchy.

a) Exact console output of ShapeApp (Math.PI = 3.14)›
  • Rectangle("Red", 5.0, 4.0) → 5.0 × 4.0 = 20.00
  • Circle("Blue", 3.0) → 3.14 × 3.0 × 3.0 = 28.26
  • Rectangle("Green", 2.0, 6.0) → 2.0 × 6.0 = 12.00
=== Rendering Canvas === Color: Red | Area: 20.00 Color: Blue | Area: 28.26 Color: Green | Area: 12.00
b) Where does runtime polymorphism happen, and how does Java resolve it?›
System.out.println(canvas[i].getDetails());

canvas[i] is declared as Shape, but at runtime holds a Rectangle or Circle. When getDetails() calls calculateArea(), Java checks the object's actual runtime type and dispatches to that class's override (dynamic method dispatch / late binding) — it can't be decided at compile time since Shape.calculateArea() is abstract.

c) Two new concrete Square subclasses›

HEADS UP The paper asks for two classes both literally named Square — that can't compile in the same package. Keep one as Square, rename the second (e.g. SquareViaRectangle), and flag this to your instructor.

// extends Shape directly
class Square extends Shape {
    private double side;
    public Square(String color, double side) {
        super(color);
        this.side = side;
    }
    public double calculateArea() { return side * side; }
}
// extends Rectangle — reuses its fields & area logic, adds nothing new
class SquareViaRectangle extends Rectangle {
    public SquareViaRectangle(String color, double side) {
        super(color, side, side); // width = height = side
    }
    // no override needed: inherited width*height == side*side
}
